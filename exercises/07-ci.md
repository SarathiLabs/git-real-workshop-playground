# 07 — Continuous integration

> Phase: `CI_CD` · ~30 minutes

## The situation

You opened a pull request. Five named checks appeared on it. You did not ask for them.

That is the point. A pull request is a proposal, and a proposal that nobody has tried to run is not ready to merge. CI is the part of the organisation that tries it, every time, without being asked, and without caring who wrote it.

The checks are not a lecture. One of them is about to go red on purpose.

## Your mission

Make a required check fail, read the failure, fix it, and watch the same check go green without opening a new pull request.

There are two traps on the backlog. Pick **one**.

### Trap A — a skipped test

Find the Issue about sorting teams by activity (or about `formatRelativeTime`).

The tests are already written. They live inside `describe.skip(...)`, which means Vitest does not run them, which means `main` is green even though the code they describe does not exist.

Your job, in this order:

1. Change `describe.skip` to `describe`
2. Push
3. Watch the **Test** check go red
4. Open **Details** and read the failure. It will tell you what it expected.
5. Implement until `npm test` is green locally
6. Push again
7. Watch the same pull request, same check, go green

Do not skip step 3. The red check *is* the lesson. If you implement first and only push when it is green, you will miss the most important part: a pull request is a living thing, and CI reruns on every push.

### Trap B — a secret

There is an Issue titled **Add a basic analytics client**. It is written the way these requests actually arrive: "put the key in the file for now, we will move it later."

Follow the Issue exactly. Commit the file. Push. Then look at the **Scan for secrets** check.

It will be red. Read the log. Then read this, because it is the part people get wrong:

> Deleting the line and committing again does not undo this. The old commit is still in the history. Anyone with the repository can read it with `git log -p`. Treat any secret that reached a shared branch as already compromised, and rotate it.

For this workshop the key is fake, so there is nothing real to rotate. In a job there would be. The fix here is:

1. Move the value to an environment variable (see `.env.example`)
2. Make sure `.env` is in `.gitignore` (it already is)
3. Push the cleaned-up file
4. Notice that `git log -p` still shows the original key

That last step is the whole point. The history remembers.

## Required checks

Look at your pull request. Five named checks run on every push:

- Lint
- Test
- Build
- Validate workshop data
- Scan for secrets

Those are **required**. A red one blocks the merge. That is the point: a pull request is a proposal, and a proposal that nobody has tried to run is not ready.

The merge box on the pull request lists exactly which required checks are missing. In a real company, some checks are advice and some are law. Here, these five are law.

## What each required check is for

| Check | What it is actually asking |
| --- | --- |
| Lint | Does this look like the rest of the codebase? |
| Test | Does the behaviour we have written down still hold? |
| Build | Does it compile and bundle? Types live here. |
| Validate workshop data | Did a registration or a wall signature come out inconsistent? |
| Scan for secrets | Did a credential just get published to sixty laptops? |

A red **Validate workshop data** after the wall exercise is the semantic-conflict lesson in CI form. A red **Scan for secrets** after Trap B is the same idea: Git merged your change just fine. The organisation still refused it.

## Done when

- You have seen a required check go red on a pull request of yours
- You opened the log, not just the red X
- You fixed it locally (`npm test` / `npm run scan:secrets` / `npm run lint`)
- You pushed to the **same branch** and watched CI rerun

## Branch protection, from the other side

Ask a volunteer (or yourself) to do this:

```bash
git switch main
echo "I was here" >> README.md
git commit -am "docs: test a direct push"
git push
```

GitHub will refuse. That refusal is the same mechanism as the merge box: `main` is not a branch you write to. It is the building everyone else is standing in.

```bash
git reset --hard origin/main
```

puts your local `main` back.

> Writing code and getting code accepted into a shared system are two different things.

## Stuck?

<details>
<summary>The Test check is red and I do not understand the log</summary>

Scroll to the first `FAIL`. Vitest prints the expected value and the received value. That pair is the spec.

Run the same thing locally so you can iterate without waiting for GitHub:

```bash
npm test
```

The CI job is `npm test` on Ubuntu. If it fails there and passes on your laptop, you probably have an uncommitted file that the check does not have.
</details>

<details>
<summary>I pushed a secret and now I am not sure what to do</summary>

For this workshop: remove it from the working tree, commit, push. Then run `git log -p` and confirm the old commit still has it. That is the demonstration.

Do **not** `git rebase` or `git reset` a branch that other people have already pulled to hide it. The history is already shared. Hiding it locally does not hide it on GitHub.

If this were a real key, the next steps would be: revoke it at the provider, issue a new one, put the new one in GitHub Actions secrets (Settings → Secrets and variables → Actions), never in the repo.
</details>

<details>
<summary>The merge button is grey even though my checks are green</summary>

The merge box lists the reason. Usually: waiting for a review, an unresolved conversation, or the branch is behind `main`. None of those are CI. See exercise 06.
</details>
